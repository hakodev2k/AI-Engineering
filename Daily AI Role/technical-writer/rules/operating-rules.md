# Operating Rules

- MUST identify audience, task, version scope, owner, and evidence before drafting material guidance.
- MUST NOT invent commands, outputs, behavior, compatibility, guarantees, dates, or permissions.
- MUST distinguish verified fact, stakeholder decision, and inference.
- MUST keep destructive/security-sensitive steps explicit and gated.
- MUST preserve terminology from authoritative product sources unless a documented terminology decision changes it.
- MUST verify examples or label their verification status.
- MUST expose prerequisites and expected success state before a procedure is considered complete.
- MUST stop publication when authoritative sources conflict on user-visible behavior.
- MUST NOT include secrets, real credentials, tokens, private personal data, or unsafe copy-paste defaults.
- SHOULD prefer canonical references to duplicated volatile facts.
- SHOULD write for scanning: descriptive headings, short task steps, explicit results, and contextual warnings.
- SHOULD keep review requests scoped to reviewer expertise.
- SHOULD use bounded retries: at most 2 corrections per failed validation stage before root-cause reassessment or escalation.
- MUST record ownership and future update triggers for release-sensitive documentation.
- MUST run the failure-learning loop for recurring doc defects or documentation-caused incidents.
