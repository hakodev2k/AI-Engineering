# Customer Success Framework

## Outcome hierarchy
1. **Business outcome** — why the customer invested.
2. **User outcome** — what users must accomplish differently.
3. **Technical outcome** — what systems/configuration/integrations must enable.
4. **Adoption signal** — observable behavior showing use.
5. **Value signal** — evidence the intended outcome is being achieved.

Do not substitute activity metrics for value without stating the limitation.

## Health dimensions
- **Value:** progress toward intended outcomes.
- **Adoption:** activation, breadth, depth, frequency, workflow completion.
- **Technical:** integration stability, incidents, performance, configuration, dependency health.
- **Stakeholder:** champion strength, decision access, ownership continuity, user engagement.
- **Delivery:** milestones, blockers, dependencies, deadline risk.

An aggregate health label is only useful when dimensions and evidence remain visible.

## Prioritization
Rank work using impact, urgency, dependency blocking, cost of delay, risk, effort, reversibility, confidence, and approval requirements. A high-impact uncertain risk can outrank a low-impact certain task.

## Evidence discipline
Facts must have sources. Assumptions must be labeled. Hypotheses need a test. Decisions need owner/date/rationale. Risks need cause-event-consequence and mitigation. Completed work needs verification evidence.

## Communication
For executives: outcome, impact, risk, decision needed, owner/date. For engineers: reproduction, environment, evidence, hypotheses, changes, dependencies. Never remove a technically material constraint when simplifying.

## Learning loop
After significant failure capture: Failure → Root Cause → Lesson → Process Improvement → Future Prevention. Prefer process changes supported by repeated or well-explained evidence.
