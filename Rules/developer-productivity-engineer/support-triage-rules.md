# Developer Support and Triage Rules
## Purpose
Resolve developer-blocking issues quickly while generating reusable learning.
## Scope
Support queues, escalations, incident-like tooling failures, and recurring friction.
## MUST
- Triage MUST distinguish user error, documentation gaps, product defects, infrastructure failures, and security concerns using evidence.
- High-impact blockers MUST have clear ownership, status, and escalation path.
- Repeated issues MUST feed backlog or documentation improvements rather than remain indefinitely manual support.
- Diagnostic requests MUST minimize collection of secrets and sensitive source data.
## MUST NOT
- MUST NOT close systemic issues solely because a local workaround exists.
- MUST NOT ask users to disable security controls as a routine workaround.
## SHOULD
- Common resolutions SHOULD become self-service diagnostics or documented runbooks.
## Exceptions
Temporary workarounds require risk disclosure and expiration criteria.
## Verification
Review ticket taxonomy, recurrence, time-to-unblock, escalations, and conversion of repeated issues into fixes.
