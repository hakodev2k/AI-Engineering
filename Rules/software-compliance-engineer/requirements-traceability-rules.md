# Requirements Traceability Rules

## Purpose
Ensure compliance obligations are translated into explicit, testable engineering requirements and remain traceable through delivery.

## Scope
Applies to legal, regulatory, contractual, certification, policy, and standards-derived requirements that affect software systems.

## MUST
- Each applicable obligation MUST map to one or more concrete engineering controls or documented non-applicability decisions.
- Traceability MUST connect source obligation, control owner, implementation evidence, verification method, and current status.
- Material requirement changes MUST trigger impact analysis before implementation or release decisions proceed.
- Unresolved compliance requirements MUST be visible to accountable owners.

## MUST NOT
- MUST NOT treat vague policy language as sufficient implementation guidance when a testable control can be defined.
- MUST NOT mark a requirement satisfied without supporting evidence.

## SHOULD
- Maintain stable identifiers for obligations and controls so evidence can be reused across audits and releases.

## Exceptions
Exceptions require documented rationale, scope, risk, compensating controls, expiration or review date, and authorized approval.

## Verification
Review traceability matrices, requirement records, control mappings, change history, evidence links, and approval records.
