# Target State Architecture Rules

## Purpose
Define credible target states that guide coordinated change without becoming speculative diagrams.

## Scope
Current-state assessment, target architecture, transition states, and strategic roadmaps.

## MUST
- Target states MUST identify business drivers, constraints, assumptions, quality attributes, and intended outcomes.
- Material gaps from current state MUST have explicit transition strategies, dependencies, and ownership.
- Target-state claims MUST distinguish committed direction from exploratory options.

## MUST NOT
- MUST NOT define a target state with no feasible migration path.
- MUST NOT hide known legacy, regulatory, data, operational, or contractual constraints.

## SHOULD
- Target states SHOULD minimize irreversible commitments until uncertainty is sufficiently reduced.

## Exceptions
Long-horizon target states may contain uncertainty when hypotheses and validation checkpoints are explicit.

## Verification
Review target-state artifacts against current-state evidence, transition plans, dependencies, and approved strategic outcomes.
