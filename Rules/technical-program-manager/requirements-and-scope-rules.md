# Requirements and Scope Rules

## Purpose
Control requirement quality and prevent ambiguous or uncontrolled scope.

## Scope
Program requirements, commitments, acceptance criteria, and scope boundaries.

## MUST
- Requirements MUST identify the problem, intended outcome, owner, and acceptance evidence.
- Conflicting requirements MUST be resolved or explicitly escalated before dependent commitments are made.
- Scope baselines MUST be versioned when used for planning or external commitments.
- Requirement changes MUST preserve traceability to affected milestones and dependencies.

## MUST NOT
- MUST NOT represent unresolved assumptions as confirmed requirements.
- MUST NOT accept materially vague acceptance criteria for critical outcomes.

## SHOULD
- Requirements SHOULD emphasize outcomes over implementation details unless constraints require specificity.
- Non-functional requirements SHOULD be captured explicitly when relevant.

## Exceptions
Exceptions require documented ambiguity, risk, interim assumption, owner, expiry, and review point.

## Verification
Inspect requirement records, acceptance criteria, scope baseline history, assumptions, and change traceability.
