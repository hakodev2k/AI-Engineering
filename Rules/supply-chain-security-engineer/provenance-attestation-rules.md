# Provenance and Attestation Rules

## Purpose
Ensure released artifacts can be traced to authorized source, build process, and inputs.

## Scope
Applies to build provenance, attestations, source revisions, builders, dependencies, and release artifacts.

## MUST
- Production artifacts MUST be traceable to an immutable source revision.
- Build provenance MUST identify the builder, source revision, and artifact digest for security-critical or externally distributed software.
- Attestations MUST be generated by trusted automation rather than self-asserted manually when automated generation is feasible.
- Verification of provenance MUST fail closed for release paths designated as high assurance.
- Attestation signing identities and trust roots MUST be governed and rotated under controlled procedures.

## MUST NOT
- Mutable tags, branch names, or filenames MUST NOT be treated as sufficient provenance evidence.
- An artifact MUST NOT be promoted merely because its checksum matches an untrusted source.
- Provenance verification MUST NOT silently downgrade when required evidence is missing.

## SHOULD
- Provenance SHOULD capture material build inputs and relevant build environment identity.
- Verification SHOULD occur at promotion or deployment boundaries, not only at artifact creation.

## Exceptions
Exceptions require documented risk, affected releases, compensating verification, expiration, and security approval.

## Verification
Inspect attestations, signatures, artifact digests, source revisions, CI identity, verification logs, and release-gate evidence.
