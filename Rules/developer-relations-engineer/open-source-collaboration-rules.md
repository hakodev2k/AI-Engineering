# Open Source Collaboration Rules

## Purpose
Support healthy open-source participation while respecting project governance, contributor trust, and organizational boundaries.

## Scope
Applies to issues, pull requests, samples, maintainership, sponsorship, community forks, and upstream contributions.

## MUST
- Contributions MUST follow the target project's contribution, licensing, security, and governance requirements.
- Organizational affiliation MUST be disclosed when materially relevant to the contribution.
- Changes that alter public behavior MUST include appropriate tests, documentation, or compatibility notes.
- Security-sensitive reports MUST use the project's approved private disclosure path when one exists.

## MUST NOT
- MUST NOT pressure maintainers for priority based on employer or commercial influence.
- MUST NOT publish confidential product plans in upstream discussions.
- MUST NOT copy code across incompatible licenses.

## SHOULD
- Contributions SHOULD solve broadly useful problems rather than maintain unnecessary private divergence.
- Maintainer feedback SHOULD be incorporated respectfully and traceably.

## Exceptions
Fork-specific behavior is acceptable when upstream inclusion is inappropriate, provided divergence, ownership, and maintenance cost are explicit.

## Verification
Review contribution history, license compatibility, governance compliance, tests, disclosure handling, and maintained divergence records.
