# API Product Reasoning

## Core model
An API is a product when consumers can reliably understand, adopt, integrate, operate, and evolve against a stable promise. Optimize for consumer outcomes rather than endpoint count.

## Decision sequence
1. Identify the consumer job and measurable friction.
2. Verify evidence and affected segments.
3. Define outcome before solution.
4. Establish contract boundaries and ownership.
5. Evaluate compatibility, security, reliability, DX, economics, and delivery cost.
6. Prefer reversible experiments when uncertainty is high.
7. Define lifecycle and migration consequences before commitment.
8. Verify adoption and task success after launch.

## Trade-offs
- More flexibility can increase contract complexity and support burden.
- Strict consistency can slow urgent consumer value.
- Backward compatibility protects trust but can increase long-term maintenance cost.
- Higher quotas improve capability but can raise reliability/security/cost risks.
- Faster launch without documentation shifts cost to support and consumers.

## Common failures
Solution-first roadmaps, proxy metrics without consumer outcomes, hidden breaking changes, ambiguous ownership, undocumented quotas, premature SLA promises, deprecations without migration evidence, and treating internal consumers as captive users.
