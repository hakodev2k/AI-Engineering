# Secure Release Artifact Rules
## Purpose
Ensure the binary delivered to users has expected code, configuration, signing, and security posture.
## Scope
Release APK/AAB/IPA or equivalent artifacts, symbols, signing, obfuscation, debug flags, and provenance.
## MUST
- Release artifacts MUST be generated by an authorized pipeline and cryptographically signed with approved identities.
- Production artifacts MUST be inspected for debug/test features, unintended endpoints, embedded secrets, and excessive permissions.
- Symbols/mapping files required for diagnostics MUST be retained securely for supported releases.
## MUST NOT
- Unsigned or ad hoc modified artifacts MUST NOT be promoted as production releases.
- Obfuscation MUST NOT be treated as a substitute for server-side authorization or secret protection.
## SHOULD
- Artifact hashes and provenance SHOULD be retained with release records.
## Exceptions
Internal development artifacts may use development signing when clearly separated from production distribution.
## Verification
Inspect signatures, manifest/entitlements, binary strings/config, artifact hash, provenance, and symbol availability.
