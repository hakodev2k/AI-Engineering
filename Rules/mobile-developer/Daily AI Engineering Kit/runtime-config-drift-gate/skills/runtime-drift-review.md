# Skill: Runtime Drift Review

## Purpose
Compare a redacted runtime snapshot with the expected configuration baseline, classify drift, and produce an evidence-based decision without exposing secrets or changing runtime configuration.

## When to use
Use after a runtime snapshot is collected and before release, rollout continuation, configuration remediation, or incident closure.

## Inputs
- Expected snapshot.
- Runtime snapshot.
- `config/drift-policy.json`.
- Optional approved exceptions.

## Preconditions
- Both snapshots validate successfully.
- Environment identifiers match.
- Snapshot freshness is within policy.
- Runtime snapshot was collected read-only.

## Allowed tools
- Read-only artifact inspection.
- `scripts/compare-config-snapshots.py`.
- `scripts/evaluate-drift-gate.py`.

## Constraints
- Do not fetch raw secret values to explain a fingerprint mismatch.
- Do not mutate runtime configuration.
- Do not downgrade severity merely because an application currently appears healthy.
- Missing critical keys are blocking unless an explicit, valid exception exists.

## Process
1. Validate both snapshots.
2. Verify target environment, application identity, and scope match.
3. Check snapshot freshness and source metadata.
4. Run the deterministic comparator.
5. Review drift categories: `missing-runtime`, `unexpected-runtime`, `type-mismatch`, `value-mismatch`, `fingerprint-mismatch`, `source-mismatch`, and `presence-mismatch`.
6. Map each drift to policy severity.
7. Attach approved exceptions only when scope, environment, key, reason, approver, and expiry all match.
8. Separate confirmed facts from hypotheses about why drift exists.
9. Run the final gate.
10. Hand blocking results to the human owner before any remediation.

## Expected output
A drift report with per-key evidence, severity, exception state, and a gate decision of `pass`, `human-approval-required`, or `block`.

## Verification
The final gate must be generated by deterministic scripts and reviewed by an agent different from the baseline producer for high-severity drift.

## Failure handling
- Invalid snapshot: block.
- Stale runtime evidence: recollect once; if still stale, block.
- Comparator/tool transient failure: retry once preserving first error.
- Permission failure: block; never request broader permissions automatically.

## Stop conditions
Stop when drift is classified and a deterministic gate decision exists. Remediation is a separate action and may require approval.
