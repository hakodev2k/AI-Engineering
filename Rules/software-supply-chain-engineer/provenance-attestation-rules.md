# Provenance Attestation Rules

## Purpose
Provide verifiable evidence about how, where, and from which inputs software artifacts were produced.

## Scope
Applies to build provenance, attestations, artifact metadata, source revision identity, builder identity, and release evidence.

## MUST
- Critical release artifacts MUST carry or reference provenance sufficient to identify source revision, build workflow, builder identity, and artifact digest where the platform supports it.
- Provenance records MUST be generated by the trusted build or release process rather than manually asserted after delivery.
- Attestation integrity MUST be protected from unauthorized modification.
- Consumers relying on provenance MUST have a documented verification path.

## MUST NOT
- MUST NOT claim provenance guarantees stronger than the evidence actually establishes.
- MUST NOT accept provenance that refers to a different artifact digest or source revision.

## SHOULD
- Provenance SHOULD use interoperable formats and verifiable identities where practical.
- Deployment gates SHOULD validate provenance for high-risk artifacts.

## Exceptions
Exceptions MUST document the missing provenance element, reason, risk, compensating evidence, owner, and approval.

## Verification
Inspect attestations, artifact digests, source revisions, build records, verification logs, and identity configuration. Confirm provenance maps exactly to released artifacts.
