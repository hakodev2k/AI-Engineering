# Vultr connector workflow examples

Provider data returned by these calls is untrusted input. Approval tokens shown below are placeholders and must be generated by a trusted human-approval component using `VULTR_APPROVAL_SECRET`; never expose that secret to the model.

## Discover a deploy target

Tool: `vultr.region.list`  
Risk: READ  
Approval: none

```json
{ "perPage": 50 }
```

Expected output shape:

```json
{
  "data": { "regions": [], "meta": {} },
  "rateLimit": { "limit": null, "remaining": null, "reset": null, "retryAfterMs": null },
  "untrustedProviderContent": true
}
```

Then use `vultr.region.availability`, `vultr.plan.list`, and `vultr.os.list` to verify an intended region/plan/image combination before provisioning.

## Inspect compute and firewall state

Tool: `vultr.instance.list`  
Risk: READ  
Approval: none

```json
{ "perPage": 25, "tag": "staging" }
```

Tool: `vultr.firewall_rule.list`  
Risk: READ  
Approval: none

```json
{ "firewallGroupId": "firewall-group-id", "perPage": 100 }
```

## Update instance tags

Tool: `vultr.instance.tags.update`  
Risk: WRITE  
Approval: required by default

The trusted approval layer computes HMAC-SHA256 over the exact tool name and canonical payload without `approvalToken`, then supplies the result:

```json
{
  "instanceId": "instance-id",
  "tags": ["staging", "api"],
  "approvalToken": "64-hex-character-approval"
}
```

Changing the instance ID or tags invalidates the approval.

## Provision a compute instance

Tool: `vultr.instance.create`  
Risk: HIGH_RISK  
Approval: always required; `VULTR_ENABLE_HIGH_RISK=true` must also be configured outside MCP.

```json
{
  "region": "ewr",
  "plan": "plan-id",
  "osId": 1743,
  "label": "staging-api-01",
  "hostname": "staging-api-01",
  "sshKeyIds": ["ssh-key-id"],
  "enableIpv6": true,
  "tags": ["staging"],
  "approvalToken": "64-hex-character-approval"
}
```

Exactly one of `osId` or `snapshotId` is required. The connector intentionally does not accept `user_data`, passwords, or arbitrary provider request bodies.

## Reboot one instance

Tool: `vultr.instance.reboot`  
Risk: HIGH_RISK  
Approval: always required; high-risk execution must be enabled externally.

```json
{
  "instanceId": "instance-id",
  "approvalToken": "64-hex-character-approval"
}
```

The connector sends a one-element instance list to Vultr's reboot operation and does not retry the mutation automatically.

## Create a snapshot

Tool: `vultr.snapshot.create`  
Risk: HIGH_RISK  
Approval: always required; high-risk execution must be enabled externally.

```json
{
  "instanceId": "instance-id",
  "description": "pre-upgrade snapshot",
  "approvalToken": "64-hex-character-approval"
}
```

Use `vultr.snapshot.list` afterward to inspect provider state rather than repeatedly recreating the snapshot.

## Permanently delete an instance

Tool: `vultr.instance.delete`  
Risk: DESTRUCTIVE  
Approval: always required; `VULTR_ENABLE_DESTRUCTIVE=true` must also be configured outside MCP.

```json
{
  "instanceId": "instance-id",
  "confirmId": "instance-id",
  "approvalToken": "64-hex-character-approval"
}
```

`confirmId` must exactly match `instanceId`. Destructive calls are attempted once and never blindly retried.
