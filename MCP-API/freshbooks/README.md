# FreshBooks MCP/API Connector

Reusable MCP server for FreshBooks accounting workflows. It exposes scoped tools for clients, invoices and expenses while keeping OAuth credentials inside the connector process.

## Upstream strategy

FreshBooks publishes an official JSON REST API and OAuth 2 authorization model. No official FreshBooks MCP server was identified in the official developer documentation researched for this connector, so all implemented capabilities use the official REST API directly. No community MCP runtime is required.

Official sources: FreshBooks API introduction (`https://www.freshbooks.com/api/start`), authentication (`https://www.freshbooks.com/api/get-authenticated-on-the-freshbooks-api`), scopes (`https://www.freshbooks.com/api/scopes`), clients (`https://www.freshbooks.com/api/clients`), invoices (`https://www.freshbooks.com/api/invoices`), expenses (`https://www.freshbooks.com/api/expenses`), paging (`https://www.freshbooks.com/api/parameters`), and webhooks (`https://www.freshbooks.com/api/webhooks`).

## Runtime

Node.js 20+ and npm.

```bash
npm install
npm run build
npm start
```

The server uses MCP stdio transport, so clients that can launch local stdio MCP servers can integrate it. Compatibility ultimately depends on the client's MCP stdio support and configuration model.

## Authentication

FreshBooks API requests use OAuth 2 bearer access tokens. Put the token only in `FRESHBOOKS_ACCESS_TOKEN`; never place it in an agent prompt. FreshBooks access tokens expire and refresh tokens are single-use: when implementing an OAuth host around this package, persist each newly returned refresh token atomically and replace the prior token. This connector deliberately accepts an already-issued access token rather than exposing OAuth secrets as MCP tool parameters.

Required least-privilege scopes depend on enabled workflows:

- Clients read/write: `user:clients:read`, `user:clients:write`
- Invoices read/write: `user:invoices:read`, `user:invoices:write`
- Expenses read/write: `user:expenses:read`, `user:expenses:write`

Set `FRESHBOOKS_ACCOUNT_ID` to the accounting account ID. Copy `.env.example` into your secret-management workflow; the server does not load `.env` automatically.

## Tools and risk model

| Tool | Operation | Risk | Approval |
|---|---|---|---|
| `freshbooks.client.list` | Paginated clients | READ | No |
| `freshbooks.client.get` | Client details | READ | No |
| `freshbooks.client.create` | Create client | WRITE | Write gate |
| `freshbooks.client.update` | Update client | WRITE | Write gate |
| `freshbooks.invoice.list` | Paginated invoices | READ | No |
| `freshbooks.invoice.get` | Invoice details | READ | No |
| `freshbooks.invoice.create` | Create draft invoice | WRITE | Write gate |
| `freshbooks.invoice.update` | Update without emailing | WRITE | Write gate |
| `freshbooks.invoice.send` | Email invoice externally | HIGH_RISK | Explicit human approval |
| `freshbooks.expense.list` | Paginated expenses | READ | No |
| `freshbooks.expense.get` | Expense details | READ | No |
| `freshbooks.expense.create` | Create expense | WRITE | Write gate |
| `freshbooks.expense.update` | Update expense | WRITE | Write gate |

Writes are disabled unless `FRESHBOOKS_ALLOW_WRITES=true`. `freshbooks.invoice.send` additionally requires an approval value equal to the connector-local `FRESHBOOKS_APPROVAL_TOKEN`. The token is compared inside the connector and should be supplied by a trusted approval broker/UI, not generated by an LLM.

Deletion, payment collection, billing changes, client deletion and other irreversible/high-impact operations are intentionally not exposed. Draft invoice creation strips `action_email` and `action_mark_as_sent`; normal invoice update strips `action_email`. External email therefore has one narrow approved tool.

## Reliability

Requests use an AbortController timeout (default 15 seconds). Retries are bounded to 0–5 attempts and occur only for HTTP 429 and 5xx responses. Validation, authentication and permission errors are not retried. `Retry-After` is preserved when supplied; otherwise exponential backoff with jitter is used.

FreshBooks documents HTTP 429 rate limiting and asks integrations to back off. Exact fixed limits are not promised by the public docs, so this connector does not invent a request quota. Pagination uses `page` and `per_page`, capped by the connector at FreshBooks' documented maximum of 100 items per page.

## Security

Provider content is returned inside `{ "untrusted_provider_data": true, "data": ... }`. Remote invoice notes, client fields and expense descriptions must be treated as untrusted data, never agent instructions. Tool names map to fixed FreshBooks paths; there is no arbitrary URL/request tool, which prevents caller-controlled SSRF through the connector. IDs are validated before path interpolation. Credentials remain in process environment/configuration and are never returned in tool results.

Use HTTPS-only official endpoints. Do not log authorization headers or approval tokens. Scope OAuth grants to only the implemented resource families actually needed. If an OAuth token needs fewer/different FreshBooks scopes, FreshBooks documents that changing consent requires revocation and a new authorization flow.

## Webhooks

FreshBooks supports webhook callbacks for real-time synchronization. This package documents but does not expose webhook subscription mutation as an agent tool because callback registration changes external delivery configuration and requires an application-owned public receiver. Prefer webhooks over aggressive polling when building a host application.

## Errors

Non-success provider responses become `FreshBooksError` with status and parsed response body. 401/403 should be handled as authentication/scope problems requiring operator action. 429 is retried within the configured bound. 5xx/network failures should be surfaced after bounded retry rather than hidden.

## Testing

```bash
npm test
```

Tests use fake fetch implementations and require no live FreshBooks credentials. They cover credential configuration, default write denial, high-risk approval, path validation, pagination/auth headers, throttling retry and non-retryable validation errors.

## Limitations

The connector intentionally covers a focused accounting workflow rather than the full FreshBooks API. It does not implement payments, checkout links, destructive deletes, uploads, reports, time tracking, projects, retainers, taxes, journal entries, webhook receivers, or OAuth browser flows. Invoice and expense payloads are passed through as provider-shaped objects after MCP structural validation; FreshBooks remains the source of truth for field-level accounting validation.
