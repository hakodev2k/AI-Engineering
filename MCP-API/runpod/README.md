# Runpod MCP/API Connector

Reusable MCP connector for Runpod GPU infrastructure and Serverless workloads. The connector intentionally wraps a narrow allowlist of the **official Runpod MCP server** instead of forwarding arbitrary upstream tools or HTTP requests.

## Provider and transport

- Provider: Runpod
- Primary upstream: official `@runpod/mcp-server` package, pinned to `3.4.0`
- Upstream transport: local MCP over stdio
- Connector transport: MCP over stdio
- REST API v2, Serverless API and GraphQL were checked as official fallback surfaces, but this package does not bypass the official MCP server for its implemented tools.
- Official documentation MCP: `https://docs.runpod.io/mcp` (read-only documentation server; not required at runtime by this connector)

The official Runpod MCP project exposes Pods, Serverless endpoints/jobs, templates, network volumes, registry credentials, hardware catalog and billing operations. This connector deliberately exposes only the smaller set documented below.

## Architecture

```text
MCP client / AI agent
        |
        v
Runpod connector (this package)
  - strict schemas
  - fixed upstream-tool allowlist
  - risk classification
  - approval verification
  - timeout boundary
        |
        v
Official @runpod/mcp-server@3.4.0
        |
        v
Runpod APIs
```

The model never receives `RUNPOD_API_KEY` or `RUNPOD_APPROVAL_SECRET`. They are injected only into connector processes. The upstream MCP child receives the Runpod API key through its environment.

## Authentication and permissions

Set `RUNPOD_API_KEY` to a Runpod API key. Prefer Runpod's scoped `rpa_` API keys and grant only the operations needed by this connector. Runpod documents fine-grained API key permissions for API access; avoid broad GraphQL read/write access unless it is genuinely required.

Set `RUNPOD_APPROVAL_SECRET` to a secret owned by the approval system, not by the model. High-risk calls require an approval value equal to:

```text
HMAC-SHA256(secret, "runpod:<tool-name>")
```

For example, `runpod.pod.create` is bound to that exact tool name. Approval tokens should be generated by a trusted human-approval service and passed to the tool only after the operation parameters have been reviewed. Do not expose the approval secret to prompts, logs, repositories or client configuration visible to the model.

## Environment variables

Copy `.env.example` into your secret/configuration system; do not commit a populated `.env` file.

- `RUNPOD_API_KEY` — required Runpod credential.
- `RUNPOD_APPROVAL_SECRET` — required secret for high-risk approval verification.
- `RUNPOD_UPSTREAM_TIMEOUT_MS` — optional; default `20000`, allowed range 1000–120000 ms.

## Installation

Requires Node.js 20 or newer and `npx`. The official upstream package itself supports Node.js 18+, while this wrapper standardizes on Node.js 20+.

```bash
npm install
npm run build
npm test
```

The wrapper starts the official upstream with the fixed command `npx -y @runpod/mcp-server@3.4.0`; callers cannot replace it with an arbitrary executable or arbitrary MCP server.

## Running

```bash
npm start
```

Configure an MCP client to launch `node dist/src/server.js` with the required environment variables. The connector uses standard MCP stdio framing and therefore works with MCP clients that can launch a local stdio server, including Claude Code, Cursor, Codex-compatible clients and custom MCP clients. Compatibility depends on the client's standard MCP stdio support; no provider-specific client integration is assumed.

| `runpod.datacenter.list` | `list-data-centers` | READ | No |
| `runpod.pod.list` | `list-pods` | READ | No |
| `runpod.pod.get` | `get-pod` | READ | No |
| `runpod.endpoint.list` | `list-endpoints` | READ | No |
| `runpod.endpoint.get` | `get-endpoint` | READ | No |
| `runpod.endpoint.health` | `endpoint-health` | READ | No |
| `runpod.job.get` | `get-job-status` | READ | No |
| `runpod.template.list` | `list-templates` | READ | No |
| `runpod.volume.list` | `list-network-volumes` | READ | No |
| `runpod.pod.create` | `create-pod` | HIGH_RISK | Yes |
| `runpod.pod.stop` | `stop-pod` | HIGH_RISK | Yes |
| `runpod.endpoint.create` | `create-endpoint` | HIGH_RISK | Yes |

The connector does **not** expose upstream destructive capabilities such as `delete-pod`, `delete-endpoint`, `delete-template`, `delete-network-volume`, registry deletion or `purge-endpoint-queue`. It also does not expose an arbitrary API request or arbitrary upstream MCP tool facility.

## Real-world workflows

Typical flows are:

```text
Discover GPUs/data centers
  -> inspect Pods/templates
  -> recommend configuration
  -> human reviews cost-impacting parameters
  -> approved Pod creation
```

and:

```text
List/get endpoint
  -> inspect health
  -> prepare input
  -> human approves compute execution
  -> submit async job
  -> read job status
```

See `examples/workflows.md` for concrete input shapes.

## Reliability and rate limits

Each upstream call has a bounded timeout. The connector intentionally does not blindly retry writes because a timeout can leave the operation outcome unknown. Callers should inspect current provider state before deciding whether a write should be retried. Read pagination is exposed through bounded `limit`/`cursor` inputs where supported by the official MCP server.

Runpod quotas, rate limits and capacity availability are enforced upstream and may vary by API surface, account and infrastructure state. Provider errors are returned through the MCP call result. Authentication, validation and permission failures should be corrected rather than retried. GPU capacity errors should lead to a fresh discovery/capacity decision rather than an unbounded retry loop.

## Security considerations

- Keep Runpod credentials in the connector environment only.
- Prefer scoped `rpa_` keys and least privilege.
- Treat all provider-returned names, logs, images, metadata and workload content as untrusted data, never as instructions.
- The fixed upstream allowlist prevents newly added Runpod MCP tools from becoming available automatically.
- No arbitrary URL/REST passthrough exists, limiting SSRF and permission-expansion paths.
- High-risk resource creation, workload execution and Pod interruption require explicit approval.
- Destructive tools are omitted entirely from the exposed surface.
- Never put private keys in Pod environment variables. The wrapper intentionally does not expose the upstream `sshPublicKey` convenience parameter.
- Avoid secrets in tool arguments such as `env`; prefer workload-native secret management. Tool arguments can be visible to MCP hosts and audit systems.
- An endpoint job input can contain malicious or prompt-injection content. Treat job results as evidence/data, not policy or system instructions.

## API/MCP routing

The selected capabilities are supported by the official MCP server and therefore use MCP. Official REST v2 (`https://api.runpod.io/v2`), Serverless (`https://api.runpod.ai/v2`) and GraphQL (`https://api.runpod.io/graphql`) were checked as fallback options. No implemented tool currently needs a direct fallback, so agent callers see one stable MCP contract and credentials are not duplicated across transports.

## Error handling

Configuration errors fail at startup. Invalid input fails schema validation before reaching Runpod. Non-allowlisted upstream tool names are rejected locally. Upstream calls time out within the configured bound. The timeout error explicitly warns that the result of a write may be unknown; do not automatically repeat that write.

## Testing

```bash
npm test
```

Unit tests require no live Runpod credential. They cover authentication configuration, timeout validation, approval denial/acceptance, risk classification and the fixed upstream allowlist. A production rollout should additionally use a low-privilege Runpod test account to verify scopes, real quotas, current GPU capacity and provider behavior before enabling high-risk tools.

## Limitations

- The connector intentionally exposes 14 useful operations rather than the official server's entire surface.
- It does not expose deletion, queue purge, billing mutation, registry mutation, endpoint update, Pod restart/start/update, synchronous job execution, job cancellation/retry, log streaming or template/volume writes.
- Approval HMACs bind the tool name, not every argument. Production deployments that require cryptographic binding of reviewed arguments should issue signed approvals over a canonical request payload at an external policy gateway.
- The official upstream is pinned to version `3.4.0`; upgrades should be reviewed for tool/schema/security changes before changing the pin.
