# Compliance Control Framework

## Purpose
Translate applicable AI obligations into implementable, testable controls with clear ownership and evidence requirements.

## When to use
Use when building an AI governance program, preparing launch gates, remediating audit findings, or harmonizing multiple regulatory requirements.

## Inputs
Applicability matrix, risk classifications, policies, architecture, existing security/privacy controls, audit criteria.

## Preconditions
Applicable obligations and system boundaries are known.

## Context to inspect
Existing enterprise control libraries, SDLC gates, IAM, logging, model lifecycle, data governance, incident response, procurement, evaluation workflows.

## Core knowledge
Effective controls are objective, attributable, testable, and mapped to evidence. One technical control may satisfy several obligations, while one regulatory requirement may need multiple preventive, detective, and corrective controls.

## Procedure
1. Decompose obligations into control objectives.
2. Reuse existing enterprise controls where adequate.
3. Define preventive, detective, and corrective controls.
4. Assign control owner and operator.
5. Specify implementation scope and frequency.
6. Define evidence generated by normal operation.
7. Define test procedure and pass criteria.
8. Map controls back to obligations and risks.
9. Identify gaps and remediation owners.
10. Version the control set and review after material changes.

## Decision points
Prefer controls embedded into engineering workflows over manual attestations when feasible. Avoid duplicate controls when one well-designed control can satisfy multiple obligations.

## Common failure patterns
Controls phrased as vague intentions, no evidence definition, ownership without operational responsibility, and mapping controls to regulations without testing implementation.

## Verification
Select sample controls and prove implementation, operation, evidence, and obligation mapping independently.

## Expected output
A control matrix containing objective, implementation, owner, frequency, evidence, test method, mapped obligations, and residual gaps.

## Stop conditions
Escalate when a mandatory obligation has no feasible control, when a control conflicts with system architecture, or when ownership cannot be assigned.
