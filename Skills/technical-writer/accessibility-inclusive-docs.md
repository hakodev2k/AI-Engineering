# Accessible and Inclusive Documentation

## Purpose
Make technical content perceivable, navigable, understandable, and usable across assistive technologies and diverse readers.
## When to use
Use for all public/internal documentation, especially critical workflows.
## Inputs
Content, platform capabilities, accessibility standards, media, code examples.
## Context to inspect
Heading structure, links, tables, images, video, keyboard navigation, contrast/platform behavior.
## Core knowledge
Accessibility is structural and semantic, not an alt-text pass. Prefer native semantic content and plain language before workarounds.
## Procedure
1. Use logical heading hierarchy and landmarks supported by the platform.
2. Write descriptive link text.
3. Provide meaningful alt text or mark decorative images appropriately.
4. Avoid images as the sole carrier of text/instructions.
5. Give tables proper headers and keep structures simple.
6. Caption/transcribe multimedia as needed.
7. Ensure instructions do not rely only on color/location.
8. Test keyboard and screen-reader paths for critical pages.
9. Check code and diagrams for accessible alternatives.
## Decision points
Use diagrams when spatial structure adds value, but provide equivalent textual meaning.
## Common failure patterns
“Click here” links, heading jumps, screenshot-only steps, layout tables, and autogenerated alt text accepted blindly.
## Verification
Run automated checks plus manual keyboard/assistive-technology review on representative content.
## Expected output
Documentation usable without relying on a single sensory or interaction mode.
## Stop conditions
Escalate platform accessibility defects that authors cannot remediate.
