# Documentation Information Architecture

## Purpose
Organize documentation so users can predict where information lives and navigate from intent to answer.
## When to use
Use for new doc sets, major growth, duplicated content, or poor findability.
## Inputs
Audience/task map, content inventory, search analytics, navigation constraints.
## Context to inspect
Current hierarchy, URLs, cross-links, product taxonomy, ownership, search queries.
## Core knowledge
Structure around user mental models and tasks. Separate tutorials, how-to guides, reference, and explanation when their reading modes differ.
## Procedure
1. Inventory content and user journeys.
2. Group by user intent rather than team ownership.
3. Define stable top-level categories.
4. Design landing pages and progressive disclosure.
5. Establish naming and URL conventions.
6. Remove duplicate canonical topics and add contextual links.
7. Test navigation with representative tasks.
8. Plan redirects for moved content.
## Decision points
Prefer shallow predictable hierarchy; introduce deeper taxonomy only when scale requires it.
## Common failure patterns
Org-chart navigation, catch-all sections, duplicate truth, orphan pages, and breaking URLs casually.
## Verification
Run findability tests and inspect search exits, dead ends, and broken links.
## Expected output
A maintainable navigation/content model with canonical locations.
## Stop conditions
Escalate when platform constraints prevent safe redirects or required ownership cannot be established.
