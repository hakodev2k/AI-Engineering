# Audience and Task Analysis

## Purpose
Identify who needs documentation, what they are trying to accomplish, and what knowledge or constraints shape successful use.
## When to use
Use before creating or restructuring product, API, operational, or developer documentation.
## Inputs
Product scope, user research, support cases, analytics, workflows, existing docs.
## Context to inspect
User roles, experience levels, environments, failure points, terminology, access constraints.
## Core knowledge
Documentation should optimize user tasks, not mirror internal architecture. Segment audiences only when needs materially differ.
## Procedure
1. Identify business/user outcomes.
2. Map primary audiences and real tasks.
3. Rank tasks by frequency, criticality, and difficulty.
4. Capture prerequisites, context, terminology, and failure modes.
5. Inspect support/search evidence for unmet needs.
6. Define documentation journeys and success evidence.
7. Validate assumptions with users or domain experts.
## Decision points
Create separate journeys when audiences require materially different prerequisites or decisions; otherwise avoid duplication.
## Common failure patterns
Writing for the author, persona theater, documenting features instead of tasks, and ignoring rare but critical recovery paths.
## Verification
Representative users can find the right starting point and complete priority tasks without hidden knowledge.
## Expected output
Prioritized audience/task map that guides documentation scope.
## Stop conditions
Stop when audience ownership or product behavior is too uncertain to document reliably.
