# Competitive Technical Evaluation

## Purpose
Compare technical alternatives fairly using customer-relevant criteria and verifiable evidence.

## When to use
Use when a customer is selecting among platforms, architectures, vendors, or implementation strategies.

## Inputs
Customer requirements, alternatives, documentation, benchmarks, test results, operational constraints.

## Context to inspect
Comparable feature scope, architecture, deployment model, limits, lifecycle, security, integration effort, operations, and switching cost.

## Core knowledge
Competitive evaluation must avoid cherry-picked benchmarks and stale claims. Differences matter only when they affect the customer's outcomes or risks.

## Procedure
1. Define decision criteria from customer requirements.
2. Establish comparable scope and assumptions.
3. Use primary documentation and reproducible tests.
4. Compare architecture and operational consequences.
5. Quantify meaningful performance/cost differences where possible.
6. Identify strengths and limitations of each option.
7. Mark unknowns explicitly.
8. Recommend based on fit, not generic superiority.

## Decision points
Run a controlled bake-off when documentation cannot resolve a decision-critical difference.

## Common failure patterns
FUD, outdated competitor claims, unequal configurations, vanity benchmarks, and ignoring migration or operating costs.

## Verification
Claims are traceable to current evidence and comparison criteria match customer priorities.

## Expected output
A balanced technical comparison with a fit-based recommendation.

## Stop conditions
Stop when evidence cannot be verified or comparison would require confidential/prohibited information.
