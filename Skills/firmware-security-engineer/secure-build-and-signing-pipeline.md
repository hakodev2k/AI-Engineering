# Secure Build and Signing Pipeline

## Purpose
Protect firmware build and signing so released binaries are reproducible, attributable, dependency-controlled, and signed only after authorized verification.

## When to use
Use for CI/CD design, release hardening, signing-service integration, build compromise response, or reproducibility work.

## Inputs
Build system, CI configuration, source controls, dependencies/toolchains, signing service/HSM, artifact repository, release approvals, and provenance requirements.

## Preconditions
Separate ordinary builds from production signing. Production private signing keys must not be directly available to developer workstations or general CI jobs.

## Context to inspect
Source revision, submodules, generated code, compiler images, dependency pinning, build runners, secrets, artifact handoff, approval gates, signing request identity, provenance, and retention.

## Core knowledge
Firmware signing converts build-pipeline compromise into trusted code execution unless signing authorization independently validates provenance. Hermetic/pinned builds and reproducibility reduce ambiguity. Artifact hashes must bind exactly what is reviewed to what is signed.

## Procedure
1. Map source-to-signed-artifact trust flow.
2. Pin toolchains and dependencies by immutable digest/version.
3. Minimize network and credential access from build workers.
4. Generate provenance containing source revision, build definition, toolchain, and artifact digest.
5. Run tests/security gates before signing eligibility.
6. Submit artifact digest plus approved metadata to an isolated signing service.
7. Enforce least-privilege signing identities and branch/release policy.
8. Keep signing keys in HSM/offline systems appropriate to risk.
9. Store signed artifact, manifest, provenance, and audit event immutably.
10. Verify signature and digest after distribution packaging.
11. Establish emergency key compromise and build-environment rotation procedures.
12. Periodically rebuild releases to assess reproducibility.

## Decision points
Fully reproducible builds offer strongest independent verification but may require deterministic timestamps/toolchains. HSM online signing supports automation; offline roots with delegated online intermediates improve root protection.

## Common failure patterns
Signing whatever CI uploads; mutable toolchain tags; dependencies fetched from unpinned URLs; signing keys as CI secrets; artifact modified after signing; provenance generated by an untrusted post-processing step; no audit of who authorized release.

## Verification
Rebuild a release from recorded inputs, compare expected hashes where deterministic, validate provenance/signature independently, inspect signing audit logs, and attempt unauthorized signing requests to confirm policy rejection.

## Expected output
Hardened build/signing workflow, provenance records, key-access policy, reproducibility evidence, and compromise runbook.

## Stop conditions
Escalate when production signing keys are exposed to general CI, build inputs cannot be pinned, signed artifacts cannot be traced to source, or required signing-policy changes need security/release authority.
