# Developer Journey Mapping

## Purpose
Map how developers discover, adopt, build, test, deploy, debug, and operate a platform or product so friction can be removed systematically.

## When to use
Use when onboarding is slow, workflows are fragmented, support load is high, or a platform team needs evidence-based priorities.

## Inputs
Developer interviews, telemetry, support tickets, docs, repositories, CI/CD flows, platform interfaces, and task completion data.

## Context to inspect
Inspect representative workflows end to end rather than isolated tools. Identify personas, environments, handoffs, permissions, waits, failures, and undocumented knowledge.

## Core knowledge
Developer experience is an outcome of cognitive load, feedback speed, reliability, discoverability, consistency, and autonomy. Optimize the journey, not vanity metrics.

## Procedure
1. Define target developer personas and jobs-to-be-done.
2. Select high-frequency or high-cost journeys.
3. Observe real execution and collect evidence.
4. Map steps, systems, waits, decisions, and failure points.
5. Quantify friction where possible.
6. Separate local symptoms from systemic causes.
7. Prioritize improvements by impact, frequency, and effort.
8. Define measurable target outcomes.
9. Implement incrementally and remeasure.

## Decision points
Automate repetitive deterministic work; document necessary complexity; redesign unnecessary complexity. Prefer paved roads when standardization reduces cognitive load without blocking legitimate exceptions.

## Common failure patterns
Designing from assumptions, measuring satisfaction alone, optimizing one tool while worsening the full flow, and ignoring experienced developers.

## Verification
Repeat the journey with representative users and compare task time, failures, interruptions, and qualitative feedback against the baseline.

## Expected output
A prioritized journey map with evidence, friction points, causes, target outcomes, and improvement actions.

## Stop conditions
Escalate when representative users or telemetry are unavailable, security constraints are unclear, or changes require ownership outside the agreed scope.
