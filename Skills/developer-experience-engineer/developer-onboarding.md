# Developer Onboarding

## Purpose
Design onboarding that gets developers to safe, meaningful contribution quickly while teaching the system knowledge they need to operate independently.

## When to use
Use when new engineers take too long to become productive, setup failures recur, or onboarding depends heavily on individual mentors.

## Inputs
Role expectations, repositories, access requirements, setup flows, architecture material, common first tasks, and new-hire feedback.

## Context to inspect
Inspect access lead times, setup automation, first build/test/deploy, domain concepts, support channels, and common blockers.

## Core knowledge
Optimize time-to-first-meaningful-contribution, not information volume. Teach context near the task where it becomes useful.

## Procedure
1. Define onboarding outcomes by stage.
2. Walk the journey from a clean identity/device.
3. Remove or automate avoidable setup steps.
4. Sequence access before it blocks tasks.
5. Provide a verified first-success path.
6. Introduce architecture and domain knowledge progressively.
7. Assign realistic starter changes with feedback.
8. Capture blockers and update the system continuously.

## Decision points
Automate stable repetitive setup; retain human interaction for context, judgment, and team relationships.

## Common failure patterns
Huge reading lists, stale setup docs, waiting days for access, toy tasks unrelated to real work, and measuring onboarding only by elapsed employment time.

## Verification
Observe new developers complete setup and first contribution, measuring blocked time, support interventions, and task success.

## Expected output
A staged onboarding journey with automated setup, verified learning paths, ownership, and outcome metrics.

## Stop conditions
Escalate when access/security policy prevents the defined onboarding outcome or role expectations are unresolved.
