# Developer Relations Metrics

## Purpose
Measure DevRel programs using metrics tied to developer success, adoption, ecosystem health, and actionable learning.

## When to use
Use for program design, quarterly reviews, budget decisions, experiments, and portfolio optimization.

## Inputs
Program goals, funnel telemetry, content analytics, community data, event data, support themes, privacy constraints.

## Context to inspect
Metric definitions, attribution windows, bot/internal traffic, segment differences, data quality, baseline, seasonality, and downstream product events.

## Core knowledge
Separate inputs, outputs, leading indicators, outcomes, and strategic impact. Attribution is often partial; use triangulation and avoid claiming causality from correlation.

## Procedure
1. Translate each program objective into observable developer behavior.
2. Define a small metric hierarchy: outcome plus diagnostic indicators.
3. Establish definitions, data source, owner, and baseline.
4. Segment by audience and adoption stage where meaningful.
5. Remove known bot/test/internal contamination.
6. Set comparison method before launching an experiment.
7. Review quantitative results with qualitative evidence.
8. Investigate unexpected movement before interpreting it.
9. Record confidence and attribution limitations.
10. Continue, modify, scale, or retire programs based on evidence.

## Decision points
Use reach metrics for distribution diagnostics, activation/retention for developer value, and qualitative research for causal hypotheses. Avoid composite scores unless components remain interpretable.

## Common failure patterns
Vanity metrics, changing definitions, last-touch attribution, counting registrations as success, ignoring denominator changes, and optimizing metrics detached from developer outcomes.

## Verification
Audit definitions and sample events, reconcile dashboards with source data, document exclusions, and ensure decisions would change if the metric moved materially.

## Expected output
A decision-oriented measurement framework with definitions, baselines, targets, caveats, and review cadence.

## Stop conditions
Stop when data collection violates policy, metric quality is insufficient for decisions, or stakeholders request unsupported causal claims.
