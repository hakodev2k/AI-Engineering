# Onboarding Engineers

## Purpose
Create a deliberate path from new hire to safe, productive ownership while preserving quality and team capacity.

## When to use
Use for new employees, internal transfers, or engineers entering a materially different domain.

## Inputs
Role expectations, system documentation, development environment, access model, team practices, roadmap, and ownership map.

## Context to inspect
Inspect setup friction, access lead times, documentation gaps, first-task suitability, mentor capacity, and historical onboarding failures.

## Core knowledge
Effective onboarding reduces uncertainty in stages: environment, domain, code, delivery, production, then independent ownership. Speed without context creates fragile productivity.

## Procedure
1. Define expected outcomes for the first weeks and months.
2. Arrange least-privilege access before it is needed.
3. Provide system, domain, team, and operational orientation.
4. Assign an accountable onboarding partner.
5. Select progressively larger real tasks with safe blast radius.
6. Include code review, testing, deployment, and observability workflows.
7. Introduce production responsibilities gradually.
8. Hold frequent feedback checkpoints.
9. Capture questions as documentation improvements.
10. Evaluate readiness against role outcomes rather than elapsed time.

## Decision points
Use structured learning for high-risk domains; prefer real work over artificial exercises once basic context exists. Delay production privileges until controls and operating procedures are understood.

## Common failure patterns
Documentation dumps, no owner, first task too large, access delays, measuring commits instead of learning, and withholding production context for too long.

## Verification
Verify the engineer can build, test, ship, diagnose a bounded issue, explain key system boundaries, and identify escalation paths appropriate to their role.

## Expected output
An onboarding plan with milestones, owners, tasks, access needs, learning goals, and readiness evidence.

## Stop conditions
Escalate when required access cannot be granted safely, no mentor capacity exists, or the role expectations materially differ from what was hired.
