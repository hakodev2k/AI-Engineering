# Work Breakdown and Delivery Planning

## Purpose
Turn approved outcomes and deliverables into a coherent execution model with manageable work, ownership, sequencing, and measurable completion.

## When to use
Use when creating or revising a delivery plan for multi-step or cross-functional work.

## Inputs
Scope, deliverables, architecture or solution constraints, estimates, team capacity, dependencies, milestones, and acceptance criteria.

## Context to inspect
Review team operating model, release process, external lead times, environments, procurement, approvals, holidays, and parallel initiatives.

## Core knowledge
A useful work breakdown is deliverable-oriented and exposes integration work, validation, deployment, transition, and operational readiness—not only implementation tasks. Planning precision should match uncertainty.

## Procedure
1. Decompose outcomes into independently verifiable deliverables.
2. Break deliverables into work packages small enough to estimate and own.
3. Add analysis, integration, testing, release, documentation, and transition work.
4. Identify dependencies and sequencing constraints.
5. Assign accountable owners without overcommitting individuals.
6. Estimate using appropriate ranges and team evidence.
7. Map work to milestones and release boundaries.
8. Validate the plan against capacity and critical dependencies.
9. Add contingency where uncertainty and risk justify it.
10. Baseline only after delivery owners challenge the plan.

## Decision points
Use rolling-wave planning when future work is uncertain; use detailed near-term plans when dependencies require coordination. Avoid false precision for discovery-heavy work.

## Common failure patterns
Planning only coding tasks, decomposing by organizational silo instead of deliverable, hiding unowned work, confusing estimates with commitments, and ignoring integration or release effort.

## Verification
Every committed deliverable has acceptance evidence, an owner, required predecessor work, and a plausible path through testing and release.

## Expected output
A delivery plan with work packages, ownership, dependencies, milestones, estimates, and validation activities.

## Stop conditions
Stop baselining when scope is unstable, key dependencies are unknown, capacity is unconfirmed, or estimates lack sufficient evidence.
