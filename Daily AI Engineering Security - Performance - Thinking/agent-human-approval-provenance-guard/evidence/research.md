# Research — Human Approval Provenance Integrity

## Category
Thinking

## Problem
Agent runtimes can incorrectly attribute an automated cancellation, queue event, timeout, or ambiguous permission transition to a human decision. Once the model sees text such as “the user declined” it can stop valid work, discard results, apologize for an action the user never took, or alter its plan around a false premise.

## Why this matters now
Two recent Claude Code reports expose complementary failure modes.

1. **Phantom human denial from an automated event.** Anthropic Claude Code issue #85408 (opened 2026-08-10, updated 2026-08-20) reports background-task notifications colliding with permission requests. The runtime produced a sentinel saying the user did not want the action although host logs contained no deny/interrupt. The reporter observed 8 phantom cancellations in one session and about 88k tokens of completed research discarded.
2. **Permission event cannot be correlated to its tool call.** Issue #83748 (opened 2026-08-04, updated 2026-08-17) measured eight `PermissionRequest` hook payloads on 2.1.221 and found `tool_use_id` in 0/8, even though `PreToolUse` and `PostToolUse` include it. The report explains why `(tool_name, tool_input)` and timing heuristics are unsafe when similar calls overlap, reorder, duplicate, or are delayed.

A related Codex report, openai/codex#30714 (2026-06-30), describes approvals in one concurrent session appearing correlated with interrupted work in another session continuing. That report is observational rather than proof of causality, but reinforces the need for session-scoped decision identity rather than ambient approval state.

## Observed evidence
- Automated background notification can result in text semantically impersonating a human deny.
- A host can have definitive logs showing no user denial while the model is told the opposite.
- Permission hooks may lack provider-authored call identity.
- Matching permission state by timing or payload similarity is not sound under concurrency.
- False attribution causes wasted work and wrong agent decisions, not merely UI inconvenience.

## Existing approaches
### Trust the runtime’s human-readable sentinel
Simple, but unsafe when the sentinel is generated by a non-human event.

### Match `(tool_name, tool_input)`
Useful for diagnostics but ambiguous when multiple calls are identical or near-identical. Issue #83748 documents this limitation and an unsuccessful downstream attempt to use bounded heuristics.

### Match the most recent pending request
Fails under concurrent calls, delayed hooks, retries, background agents, reordering, or duplicate delivery.

### Prompt the model to “ask again when unsure”
Can reduce damage but does not repair provenance. It also adds latency and may train the agent to ask unnecessary confirmations.

## Gap
Agent hosts need a deterministic layer that separates **event semantics** from **human intent**. A deny/approve/interrupt should only become a human decision if there is provider- or host-authored evidence binding the decision to the session and, ideally, the exact tool call/request. Ambiguous events should be classified as `unknown/system`, not rewritten into “the user said no.”

## Root-cause hypotheses
1. Human-readable control messages are reused for multiple internal causes.
2. Queue/system events and user events share a downstream channel without preserved provenance.
3. Permission lifecycle events lack stable correlation identifiers.
4. Consumers reconstruct identity from timing and payload similarity.
5. Models receive conclusions (“user declined”) instead of evidence (`source=system`, `reason=queue_preempted`).

## Improvement target
Introduce a **Human Approval Provenance Guard** with:
- an append-only decision ledger;
- session/request/tool-call correlation keys;
- explicit source taxonomy (`human`, `system`, `runtime`, `watchdog`, `unknown`);
- fail-closed attribution: only `source=human` may produce “user approved/denied/stopped” semantics;
- reconciliation of permission request → decision → tool start/result;
- deterministic detection of orphan, duplicate, cross-session, stale, and source-mismatched decisions;
- correction output for the agent such as “permission outcome is unverified; do not attribute it to the user.”

## Success metrics
- False human-attribution rate: **0** in deterministic regression fixtures.
- Cross-session decision acceptance: **0**.
- Orphan decision acceptance: **0**.
- Duplicate conflicting decisions silently accepted: **0**.
- Verified decision coverage: percentage of permission outcomes with exact request/call correlation.
- Recovery cost: bounded to one reconciliation attempt before escalation.
- Rework/wasted-token impact can be measured by comparing tasks aborted due to phantom denial before and after integration.

## Interpretation vs proposed solution
The public reports prove concrete provenance/correlation gaps. They do not prove every agent runtime has the same implementation bug. The package therefore provides a host-side invariant layer rather than claiming an upstream universal root cause.
