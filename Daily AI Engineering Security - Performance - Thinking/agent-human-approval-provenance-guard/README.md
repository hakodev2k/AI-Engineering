# Agent Human Approval Provenance Guard

## Topic
Human approval provenance integrity for AI agents.

## Category
**Thinking** — improving agent decision quality by preventing unsupported conclusions about what a human approved, denied, or stopped.

## Problem
Agent runtimes increasingly mix human interaction, background agents, queue notifications, watchdogs, retries, tool hooks, and concurrent sessions. If those channels lose provenance or stable correlation, an automated event can be presented to the model as a human decision. The model then reasons from a false fact: it may halt valid work, discard completed results, retry unnecessarily, or tell the operator they denied an action they never saw.

## Evidence
Recent public reports show both sides of the failure:
- Anthropic Claude Code #85408 reports a background task notification causing a pending permission path to emit wording that impersonated a user denial. The reporter observed 8 phantom cancellations, zero recorded human denies/interrupts, and about 88k tokens of completed work discarded in one session.
- Claude Code #83748 reports that `PermissionRequest` lacks `tool_use_id`; measured captures found it in 0/8 payloads although adjacent lifecycle hooks include it. This prevents exact correlation between a prompt and the tool call it gates and makes timing/payload heuristics unsafe under concurrency.
- OpenAI Codex #30714 provides a related observational report around concurrent sessions and apparent cross-session approval/task isolation, reinforcing the value of session-scoped identity.

See `evidence/research.md` for sources, limitations, and interpretation.

## Existing approach
Common integrations trust runtime-generated human-readable sentinels, match permission prompts by tool name/input, or associate the latest pending prompt with the next decision. Some projects add instructions telling the model to ask again if unsure.

## Existing limitations
These approaches confuse evidence with inference. Identical tool calls can overlap; events can reorder, duplicate, delay, or be generated by background systems. Free-text messages can also reuse human-denial wording for a non-human cause. Prompt instructions cannot restore identity that was dropped upstream.

## Proposed improvement
Add a deterministic provenance gate between runtime events and model reasoning:

`event sources -> normalized lifecycle records -> append-only decision ledger -> exact correlation/provenance checks -> verified state -> model context`

Only a decision explicitly sourced from a trusted human interaction channel and bound to the correct session/request (plus provider tool-call ID when available) may become “the user approved/denied/stopped”. Everything else remains non-human, ambiguous, expired, or unresolved.

## Architecture
### Inputs
- permission requests;
- human UI/API decisions;
- runtime/background/system cancellations;
- tool start/results;
- session/request/tool-call identifiers;
- timestamps and policy version.

### Core components
- `config/policy.json` — fail-closed policy and source taxonomy.
- `scripts/provenance_guard.py` — deterministic JSONL validator.
- lifecycle hooks described in `hooks/hooks.md`.
- workflow and delegation contracts for investigation, implementation, and independent verification.

### Outputs
- `verified_human` decision records;
- `non_human` outcomes;
- explicit violations for orphan, cross-session, stale, conflicting, or unsupported human attribution;
- machine-readable verification report when requested.

## Installation
Requirements: Python 3.9+ and a host integration capable of exporting normalized permission lifecycle events.

No third-party Python packages are required.

Copy the package into the repository or agent-host project. Keep `config/policy.json` under version control and review policy changes like authorization changes.

## Configuration
Important defaults in `config/policy.json`:
- only `source=human` qualifies for human attribution;
- session/request identity is mandatory;
- provider `tool_use_id` must match when available;
- human decisions expire after the configured age;
- ambiguous, cross-session, orphan, and conflicting outcomes fail closed;
- reconciliation is bounded to one retry.

Customize the source taxonomy to match your host, but never classify automated channels as human merely to reduce friction.

## Usage
Validate known-good lifecycle events:

```bash
python scripts/provenance_guard.py tests/good.jsonl --policy config/policy.json
```

Expected: exit `0`.

Validate adversarial events:

```bash
python scripts/provenance_guard.py tests/bad.jsonl --policy config/policy.json
```

Expected: exit `2` with provenance violations.

Generate a report:

```bash
python scripts/provenance_guard.py path/to/events.jsonl --policy config/policy.json --report provenance-report.json
```

## Workflow
The primary workflow is:
1. Observe the permission request and preserve authoritative IDs.
2. Capture the candidate decision with true source metadata.
3. Correlate exact session/request/tool-call identity.
4. Validate freshness, duplicates, conflicts, and source.
5. Classify the outcome.
6. Hand only a provenance-safe message to the model.
7. Independently verify changes affecting approval semantics.

See `workflows/workflows.md` for incident investigation and provider-without-ID paths.

## Rules
The central invariant is simple: **human-readable text is not proof of human intent**. The proof is a trusted human-source event bound to the correct decision contract.

Full MUST / MUST NOT / SHOULD rules are in `rules/engineering-rules.md`.

## Subagents
- **Event Provenance Analyst** builds the factual ledger without guessing intent.
- **Implementation Agent** integrates source preservation and correlation.
- **Independent Verification Agent** challenges the implementation with concurrent and adversarial cases.

The implementation agent is not allowed to be the sole verifier.

## Hooks
Integrate controls at four lifecycle boundaries:
- before permission request;
- when a decision arrives;
- immediately before model-context handoff;
- after tool result;
- plus a final release verification hook.

Details are in `hooks/hooks.md`.

## Metrics
Primary metrics:
- false human-attribution rate;
- verified-human decision coverage;
- orphan/cross-session/conflicting-decision count;
- ambiguous-event rate;
- provenance-gate latency;
- agent turns/rework/tokens lost after phantom denials.

Do not claim improvement until pre/post measurements are available in the target runtime.

## Verification
### Implemented
This package implements policy, deterministic validation logic, actionable skills/rules/workflows/hooks, and good/bad regression fixtures.

### Measured
Public evidence contains measured failures from upstream reports; your own runtime still requires a local baseline before optimization claims.

### Verified
For integration, verification requires:
- good fixture exits 0;
- bad fixture exits 2;
- background/system cancellation cannot generate a human-intent assertion;
- cross-session decisions are rejected;
- orphan and conflicting decisions are rejected;
- exact tool-call identity is enforced when available;
- independent reviewer confirms the lifecycle path.

## Safety
This guard never grants permission. It protects attribution and decision integrity. Missing identity must not become auto-approval. Dangerous or irreversible operations still require the host’s normal authorization controls and explicit human approval when policy requires it.

Do not log secrets or full sensitive tool payloads solely for correlation. Prefer stable IDs, normalized metadata, or hashes.

## Failure handling
### Detection
Guard violation, missing identity, conflict, stale decision, unsupported human attribution, or mismatch between host logs and transcript claim.

### Evidence
Retain sanitized lifecycle metadata, policy version, and IDs. Keep system/background source evidence separate from user actions.

### Retry policy
One reconciliation retry maximum using authoritative host/provider state.

### Fallback
Classify as ambiguous/non-human and emit neutral wording. Do not attribute intent.

### Escalation
Require fresh explicit human action only when the blocked tool operation still needs authorization.

### Stop condition
Stop automated reconciliation after the bounded retry or any confirmed integrity violation.

## Definition of Done
A target integration is complete when:
- public/problem evidence is documented;
- local baseline is captured;
- every decision path preserves source and session/request identity;
- provider tool-call identity is used when available;
- no non-human event can impersonate human intent in regression tests;
- cross-session/orphan/stale/conflicting decisions fail closed;
- good and adversarial fixtures produce expected exit codes;
- metrics are collected;
- independent verification passes;
- approval/security boundaries are not weakened;
- unresolved provider identity gaps are documented instead of hidden.

## Customization
Extend `policy.json` with your runtime’s source names and freshness threshold. Add fixtures for provider-specific event shapes, SDK reconnects, queued notifications, concurrent subagents, approval UIs, and session resume. If upstream APIs add a stable permission-request/tool-call ID, map it directly instead of keeping heuristic correlation.
