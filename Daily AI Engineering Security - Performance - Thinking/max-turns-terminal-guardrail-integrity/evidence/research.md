# Research — Max-Turns Terminal Guardrail Integrity

## Topic
Max-Turns Terminal Guardrail Integrity

## Category
Security / Thinking

## Problem
Agent runtimes can have multiple terminal paths: normal final output, guardrail tripwire, max-turns exhaustion, refusal, cancellation, and error-handler-produced fallback output. A fallback produced by a terminal error handler can bypass the same output-guardrail and session-persistence semantics expected for normal final output, creating a policy gap exactly when the agent is already in an abnormal state.

## Why it matters now
A fresh OpenAI Agents SDK issue opened 2026-08-13 reports that `max_turns` handler output bypasses output-guardrail session semantics. A separate August 2026 issue reported streaming/non-streaming divergence around output-guardrail persistence. Current official docs describe both output guardrails and max-turns handlers, making terminal-path equivalence an observable engineering contract.

## Affected users
Teams running tool-using agents with safety output guardrails, durable sessions, streaming, retry/error handlers, compliance filters, or human approvals.

## Current public evidence
### Observed evidence
1. OpenAI Agents SDK issue #4393, opened 2026-08-13, reports that output returned from a `max_turns` handler can bypass output-guardrail session semantics. The issue references previous fixes around committed tool records, max-turn handler session output, and streamed guardrail state: https://github.com/openai/openai-agents-python/issues/4393
2. OpenAI Agents SDK issue #4125, opened 2026-08-02, reports a streamed resumed approval path where an output-guardrail tripwire left an orphaned `function_call` without matching `function_call_output`, while non-streaming persisted both: https://github.com/openai/openai-agents-python/issues/4125
3. Official OpenAI Agents SDK guardrail docs state that output guardrails validate final agent output and describe specific session-persistence behavior for tripwires, including parity between streaming and non-streaming runs: https://openai.github.io/openai-agents-python/guardrails/
4. Official run-error-handler docs expose handlers including `max_turns` whose result contains a `final_output`, while running-agent docs describe `MaxTurnsExceeded` and the agent loop: https://openai.github.io/openai-agents-python/ref/run_error_handlers/ and https://openai.github.io/openai-agents-python/running_agents/

## Existing approaches
- Define output guardrails on the agent/run.
- Define a `max_turns` cap and optionally a handler that returns a user-facing fallback.
- Persist session items through SDK-managed terminal paths.
- Add framework regression tests for individual bugs.

## Remaining limitations
- Teams often assume all terminal outputs pass the same policy checks without testing each terminal path.
- Error-handler output can be treated as operational fallback rather than a candidate final output requiring normal validation.
- Session consistency and output-policy enforcement can fail independently.
- Streaming, resumed approvals, and terminal exceptions multiply path combinations and increase regression risk.

## Root-cause analysis
1. Terminal output production and terminal output admission are separate concerns but are not always centralized.
2. Error-handler outputs can enter a shortcut path that does not reuse the normal final-output guardrail pipeline.
3. Session persistence ordering may differ between streaming and non-streaming paths.
4. Tests often validate happy-path output guardrails but not terminal-path equivalence.
5. Applications lack a deterministic contract asserting that every externally delivered terminal output has a guardrail verdict and consistent session state.

## Improvement opportunity
Add a terminal-output integrity gate around the runtime boundary. Every candidate terminal output—normal or generated by `max_turns`/other handlers—must carry a guardrail verdict before delivery. The gate separately verifies session invariants: no orphaned tool calls, rejected candidate output not persisted as accepted output, and equivalent persistence semantics across streaming/non-streaming fixtures.

## Goal
Make terminal-path policy enforcement and session consistency observable and testable rather than assumed.

## Metrics
- Delivered terminal outputs lacking a guardrail verdict: 0.
- Orphaned tool calls in terminal fixtures: 0.
- Streaming/non-streaming session parity failures: 0 for equivalent fixtures.
- Max-turn fallback blocked when guardrail rejects it: 100%.
- Maximum verification retries: 1; no unbounded retry loop.

## Trigger / Inputs / Outputs
- Trigger: immediately before delivering any terminal output and after terminal session persistence.
- Inputs: terminal reason, candidate output, guardrail verdicts, session item manifest, streaming flag, handler identity.
- Outputs: allow/block verdict, session-integrity verdict, violations, evidence record.
