# Research — Agent Convergence Progress Circuit Breaker

**Topic:** Long-running agents that continue without measurable progress  
**Category:** Thinking  
**Research date:** 2026-08-26 (UTC+7)

## Problem
Long-running coding agents can remain active while producing repeated continuation turns, expanding review/process scaffolding, polling stale state, or revisiting completed work without reducing the task's acceptance gap.

## Why it matters now
Recent public reports show hours-long or even multi-billion-token agent runs that fail to converge despite finite goals. The recurring weakness is observable control-flow: agents often lack a deterministic definition of progress, a bounded work-expansion budget, and a circuit breaker for repeated no-progress turns.

## Affected users
Developers using coding agents, engineering teams running unattended tasks, orchestration/platform builders, and multi-agent workflow maintainers.

## Current public evidence

### Observed evidence
1. OpenAI Codex issue #37800, opened August 10, 2026, reports a runaway automatic-continuation loop that repeatedly emitted only a continuation message while making no edits or meaningful progress, consuming tokens until the goal was marked blocked: https://github.com/openai/codex/issues/37800
2. OpenAI Codex issue #35892, opened July 29, 2026, reports a finite multi-repository task repeatedly expanding into new tasks, subagent lanes, review cycles and verification gates over roughly three days instead of reducing one evidence-backed critical path: https://github.com/openai/codex/issues/35892
3. OpenAI Codex issue #39512, opened August 19, 2026, reports more than five hours spent on a task with zero originally reported bugs fixed, no deployment, no live verification and repeated user intervention: https://github.com/openai/codex/issues/39512
4. OpenAI Codex issue #37282, opened August 6, 2026, reports one unattended session running 16.5 hours, issuing 7,395 model requests and consuming 4.2 billion tokens; the reporter explicitly requests max-turn/token/time ceilings and detection of repeated near-identical cached context with no measurable progress: https://github.com/openai/codex/issues/37282

### Interpretation
These reports describe different surfaces but a common orchestration defect: natural-language intent to "continue until done" is not an enforceable convergence contract. Without observable acceptance rows, artifact/evidence deltas, bounded task creation and terminal stop conditions, continuation itself can become the default action.

## Existing approaches
- Prompt instructions such as "continue until complete" or "do not stop early."
- Human monitoring and manual interruption.
- Max-token or wall-clock limits.
- Reviewer subagents and repeated verification.
- Task lists generated by the model.

## Remaining limitations
- Prompt-only stop instructions are not deterministic.
- Pure time/token ceilings stop waste but cannot distinguish slow progress from zero progress.
- Reviewer loops can create more work than they close.
- Model-generated task lists can expand without a stable acceptance baseline.
- Tool activity is not equivalent to task progress; repeated tests or status checks can look active while the acceptance gap remains unchanged.

## Root-cause analysis
1. Progress is inferred from prose rather than measured from state transitions.
2. Acceptance criteria are not represented as a stable ledger with explicit open/closed status and evidence.
3. New work can be added without tying it to a failed acceptance criterion.
4. Repeated continuation turns do not require artifact, evidence, or acceptance-gap change.
5. Retry/review loops lack bounded counters and escalation states.
6. Finalization and continuation decisions are not checked against the same task state.

## Improvement opportunity
Introduce a deterministic convergence ledger and circuit breaker. Each agent turn records acceptance rows remaining, artifact/evidence fingerprint, meaningful-change count, spawned work count, model/tool calls and terminal-state evidence. A no-progress streak or unbounded work expansion blocks automatic continuation. New work must reference an existing failed acceptance row or an explicitly approved scope change. The guard does not request hidden chain-of-thought; it checks only observable task state.
